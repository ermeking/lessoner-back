# Готовность PR в edu-api

## 1. Прогони проверки

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm test:e2e
```

Всё должно пройти. Если что-то падает не из-за твоих изменений, опиши это в PR, а не отключай проверку.

## 2. Пройди чек-лист

**Задача**
- [ ] Выполнены все пункты «Готово, когда» из текста задачи в `docs/ROADMAP-BACKEND.md`.
- [ ] Не сделано ничего сверх задачи (функции будущих версий, «заодно отрефакторил»).

**Контракт**
- [ ] У каждого нового или изменённого эндпоинта есть `operationId` из `docs/ARCHITECTURE-BACKEND.md` (раздел 6), тип ответа и `@ApiErrors`.
- [ ] Таблица эндпоинтов в `docs/ARCHITECTURE-BACKEND.md` обновлена.
- [ ] В `/api/docs-json` нет ответов с типом `object` или без схемы.

**Данные и безопасность**
- [ ] Контроллеры возвращают только DTO; `passwordHash`, `tokenHash` и `solution` не утекают.
- [ ] Проверки доступа идут через `AccessService`, данные пользователя фильтруются по `userId` из сессии.
- [ ] Новые коды ошибок есть в `docs/DOMAIN-SHARED.md` и `src/common/error-codes.ts`.
- [ ] Миграция одна, с понятным именем; SQL прочитан; применённые миграции не тронуты.

**Тесты**
- [ ] Новая бизнес-логика покрыта юнит-тестами, эндпоинты — e2e (успех, доступ, ошибки).

## 3. Опиши PR

```markdown
## <ID>: <название задачи>

### Что сделано
- …

### Принятые решения
- … (то, чего не было в документации, и почему выбран такой вариант)

### Изменения контракта
- Новые/изменённые эндпоинты: `operationId`, …
- Новые коды ошибок: …
- Фронтенду нужно: перегенерировать клиент / добавить переводы кодов / ничего

### Изменения БД
- Миграция `<имя>`: … (или «нет»)

### Как проверить руками
1. …
```

Если в ходе задачи менялся `docs/DOMAIN-SHARED.md`, напиши в PR отдельной строкой: **«DOMAIN.md изменён — обновить копию в edu-web»**.
