# Как агенту идти по роадмапу

> Этот документ — рабочий цикл. Он отвечает на вопрос «что делать дальше» и позволяет продолжить работу в новой сессии с того места, где остановилась прошлая.

## Главное правило

**Контекст сессии не вечен.** Агент не может держать в голове весь проект и не помнит прошлые сессии. Поэтому состояние проекта живёт не в памяти агента, а в файле `PROGRESS.md` в корне репозитория. Он обновляется после каждой задачи и читается первым делом в новой сессии.

Если `PROGRESS.md` не соответствует реальности, весь цикл ломается: агент возьмётся за сделанное или пропустит несделанное. Поэтому его обновление — обязательная часть задачи, а не формальность.

## Цикл работы

```
1. Прочитать PROGRESS.md
2. Определить следующую задачу
3. Проверить, готовы ли её зависимости
4. Выполнить задачу
5. Прогнать проверки и самопроверку (скилл pr-ready)
6. Обновить PROGRESS.md
7. Отчитаться и остановиться
```

### Шаг 1. Прочитать состояние

Открой `PROGRESS.md`. В нём: какие задачи завершены, какая в работе, что осталось, и заметки от предыдущих сессий (принятые решения, известные проблемы, вопросы владельцу).

Если файла нет — значит, это первая сессия: создай его по шаблону из раздела «Шаблон PROGRESS.md» ниже и начни с первой задачи роадмапа.

### Шаг 2. Определить следующую задачу

Возьми первую задачу роадмапа, которая ещё не завершена. Порядок задач не выбирается произвольно: он отражает зависимости.

Если в `PROGRESS.md` какая-то задача помечена как «в работе», сначала выясни, что от неё осталось: посмотри последний коммит и незакоммиченные изменения. Доделай её, а не начинай новую.

### Шаг 3. Проверить зависимости

У задачи в роадмапе указано поле «Зависит от». Проверь, что эти задачи завершены. Отдельно проверь зависимости от других репозиториев (таблица точек синхронизации в `README.md` пакета).

**Если зависимость не готова — не обходи её и не заглушай.** Остановись и сообщи владельцу, чего не хватает. Работа «пока без API, потом перепишем» почти всегда создаёт больше работы, чем экономит.

### Шаг 4. Выполнить задачу

Делай только то, что описано в задаче. Соблазн «заодно поправить» и «сразу сделать на будущее» — главная причина, по которой задачи разрастаются и их становится невозможно проверить.

Если по ходу нашлась проблема за пределами задачи, не чини её молча: запиши в `PROGRESS.md`, в раздел «Замечено по пути».

Если нужно решение, которого нет в документации, выбери самый простой рабочий вариант, продолжай и обязательно запиши его в отчёт. Не выдумывай бизнес-правила: их источник — `docs/DOMAIN-SHARED.md`.

### Шаг 5. Проверки

Прогони проверки:

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm test:e2e
```

Затем пройди скилл `pr-ready`.

Если проверки падают дважды подряд и причина непонятна — остановись и опиши проблему. Долгие попытки угадать вслепую тратят контекст и обычно заканчиваются хуже, чем вопрос владельцу.

### Шаг 6. Обновить PROGRESS.md

Перенеси задачу в «Завершено», добавь дату и одну строку о результате. Запиши принятые решения, вопросы владельцу и найденные по пути проблемы. Пиши так, чтобы следующая сессия поняла всё без этой переписки.

### Шаг 7. Отчитаться и остановиться

Дай короткий отчёт: что сделано, какие решения принял, что проверить владельцу, какая задача следующая. **После этого остановись.** Следующую задачу начинай, только когда владелец скажет продолжать.

## Когда остановиться и спросить

Останавливайся сразу, не пытаясь решить самостоятельно:

- зависимость задачи не готова;
- задача требует решения владельца: название, домен, цены, платёжный провайдер, выбор между вариантами продукта;
- нужны доступы или секреты (ключи, пароли, аккаунты);
- документация противоречит сама себе или задаче;
- проверки падают дважды подряд без понятной причины;
- чтобы выполнить задачу, придётся нарушить правило из `CLAUDE.md` или изменить бизнес-правило.

Остановка — это нормальный результат сессии, а не провал. Ошибка, тихо унесённая в следующие пять задач, стоит намного дороже.

## Режимы работы

**По одной задаче (по умолчанию).** Одна задача — одна сессия — один PR — проверка владельцем. Так стоит работать всегда в начале, пока не станет ясно, насколько точны документы.

**Несколько задач подряд.** Владелец может разрешить сделать подряд несколько задач одной вехи. Даже в этом режиме действуют правила: после каждой задачи обновляется `PROGRESS.md` и делается отдельный коммит, а при любом стоп-условии работа прекращается. Задачи, затрагивающие деньги, доступы, безопасность и схему БД, в этот режим не входят: их владелец принимает поштучно.

## Особенности этого репозитория

- **Схема БД и миграции.** Задача, меняющая схему, всегда завершается остановкой: миграции на продакшне необратимы, и владелец должен увидеть SQL до того, как он уедет дальше. Скилл `prisma-change` обязателен.
- **Контракт с фронтендом.** Если задача добавила или изменила эндпоинт, в отчёте обязательно строка: «фронтенду нужно перегенерировать клиент (`pnpm api:gen`)» и список изменённых `operationId`.
- **Бизнес-правила.** Все правила доступа берутся из `docs/DOMAIN-SHARED.md`. Если правила для случая нет — это вопрос владельцу, а не повод придумать своё.

## Шаблон PROGRESS.md

```markdown
# Прогресс: edu-api

Обновляется после каждой задачи. Источник задач — `docs/ROADMAP-BACKEND.md`.

## Текущая веха
Веха 0. Фундамент

## В работе
API-01 — ещё не начата

## Завершено
<!-- ID · дата · одна строка о результате -->

## Принятые решения
<!-- Решения, которых не было в документации. ID задачи + суть + почему так. -->

## Вопросы владельцу
<!-- Без ответа на них работа не идёт дальше. -->

## Замечено по пути
<!-- Проблемы за пределами задач: не чинить молча, обсудить с владельцем. -->
```

## Запуск сессии

```
Ты работаешь в репозитории edu-api.
Прочитай CLAUDE.md и docs/EXECUTION-BACKEND.md, затем работай по циклу из этого документа.
Первая задача — API-01.
```

Если нужно выполнить конкретную задачу, добавь: «Начни с задачи <ID>».
